# Traffic re-signed by a CA local to this machine - scenario S-1.
#
# THE ONE THING THIS SCENARIO EXISTS TO PROVE: that noticing this does NOT
# depend on recognising a vendor's name. mitmproxy's root is not called Zscaler,
# Netskope or anything else on any list we could write. If certdoctor needs the
# name to notice, the whole layer is built the wrong way round - O11.
#
# ---------------------------------------------------------------------------
# REWRITTEN A SECOND TIME, 2026-08-19, AND THIS TIME THE FILE ITSELF WAS WRONG.
#
# The version before this one expected interception_detected=yes while also
# recording root_in_any_trust_store=no and, three lines further down,
# distinguishable_from_no_intermediate_by=issuer. Read together those three
# lines demand exactly what O11 forbids: a detection resting on the ISSUER'S
# NAME, because on that bench nothing else separated this scenario from a server
# that had simply forgotten its intermediate.
#
# WHAT WAS MEASURED 2026-08-19, AND IT KILLED THE HEURISTIC THAT WOULD HAVE BEEN
# WRITTEN OTHERWISE. Two runs of the real binary, in this container, with a root
# deployed into one store and not the other - the shape a group policy push
# produces on a real machine:
#
#   middlebox        L4 FAIL chain_complete=false   curl trusts | git unknown_authority
#   honest internal  L4 PASS chain_complete=true    curl trusts | git unknown_authority
#
# The trust-store signature is IDENTICAL. Only chain completeness differed, and
# that is a property of mitmproxy rather than of interception: fed an
# INTERMEDIATE instead of its own root, the same middlebox presented leaf plus
# intermediate plus root - a complete chain, the same three subjects the honest
# server serves, differing in nothing but the leaf's fingerprint, which nothing
# on this machine has anything to compare against. Measured the same day.
#
# SO THE STRUCTURE NEVER SEPARATES THEM, and a program that accused on structure
# alone would accuse every internal service running under a company's own
# certificate authority - which is scenario S-3, one of the six this product was
# built for. Inviolable rule 21 calls that harm rather than a defect.
#
# WHAT CERTDOCTOR SAYS INSTEAD, and it is the honest half of the same finding:
# WHO signed the leaf, and HOW WIDELY this machine holds that signer. That fact
# is what the user came for - it is why one tool works and another does not, and
# it is what the commands repair. Naming it as interception waits for a match
# against the inspection-product list, which is P6b-K2, and until then the
# sentence names both readings and accuses neither.
# ---------------------------------------------------------------------------
#
# HOW THE BENCH PRODUCES IT. mitmdump runs a reverse listener on port 443 at
# 172.28.0.81, and registry.example.net resolves there. It terminates TLS, mints
# a leaf for whatever name was asked for signed by a root it generated at its own
# startup, and forwards to the origin at partner.test. That is the shape of every
# TLS-inspecting middlebox, without buying one.
#
# NO PROXY IS INVOLVED AND THAT IS WHY THIS FILE FINALLY HAS A READER. The
# previous version needed HTTPS_PROXY, certdoctor has no way to dial through a
# proxy - that is L2, slice P8 - and so nothing could ask this scenario anything.
# A reverse listener is reached by connecting to it, which certdoctor does today.
# The forward proxy on 8080 is untouched and still waits for P8.

target=https://registry.example.net/

# --- bench: verifiable with an independent tool ---
#
#   openssl s_client -connect registry.example.net:443
#           -servername registry.example.net -showcerts
#
# ONE certificate. The middlebox does not send its own root, so the issuer of the
# leaf is the subject of nothing that arrived - structurally incomplete, exactly
# as a server that forgot its intermediate would be.
chain_certs_presented=1
leaf_subject_cn=registry.example.net
leaf_issuer_cn_contains=mitmproxy
intermediate_presented=no

# The origin's own issuer, for comparison. Two different issuers for one piece of
# traffic, depending only on whether the box is in the way. CERTDOCTOR NEVER SEES
# BOTH HALVES IN ONE RUN - it sees whichever path it was sent down, which is
# exactly the position a user is in, and is why this pair is written down here
# rather than expected of the program.
origin_leaf_issuer_cn=certdoctor testbed intermediate

# --- what the container's two stores are made to look like ---
#
# THE ROOT IS DEPLOYED INTO ONE STORE AND NOT THE OTHER, which is what a group
# policy push does on a real machine: the platform store gets the certificate and
# the runtimes carrying their own bundles do not. curl is pointed at a copy of
# the image bundle WITH the root appended, git at a copy WITHOUT it. Both are
# real files with real paths, and neither is the image's own bundle - so no other
# scenario in this run is affected by what happens here.
root_deployed_to=curl
root_withheld_from=git

# The authority itself, mounted read only from the volume mitmproxy generates it
# into. It exists nowhere else - a middlebox root is not on the wire, which is
# why the command below has a placeholder where the certificate goes.
root_pem=/mitmconf/mitmproxy-ca-cert.pem

# THE RUNTIME THAT WAS GIVEN THE AUTHORITY IS THE WITNESS, and an exit of 0 says
# the TLS handshake was accepted - which is the fact the deployment was for.
#
# WHAT THE ZERO DOES NOT SAY, WRITTEN DOWN RATHER THAN GLOSSED: the page behind
# it is a 502. mitmproxy cannot verify the origin, which serves a private root it
# was never given, so it terminates the client's connection and fails its own.
# Nothing in M1 looks above TLS, and a scenario that gave the middlebox the
# origin's root would make it mint a certificate copying the ORIGIN's name rather
# than the one that was asked for - measured 2026-08-19 - which is a second
# difference between the two paths and not the one being studied.
curl_exit_code=0

# --- L4: structural, and it FAILS - the same value no-intermediate.txt expects
#
# THE L4 STATUS ALONE CAN THEREFORE NEVER BE THE DETECTION, which is the sentence
# this file has carried from the beginning and the only one that survived both
# rewrites intact.
l4_status=FAIL
chain_complete=false

# --- L5: the matrix S-1 was always about ---
#
# One store accepts this traffic and one does not, on one machine, at one moment.
# That is "the browser works and npm install does not" reproduced in a container.
l5_status=FAIL
l5_rows_not_trusting=1
l5_trust_failure=unknown_authority

# --- P6b: who signed it, and how widely this machine holds them ---
#
# some_stores is the measured answer and it is NOT an accusation. It says the
# signer is present here and is not part of what the runtimes shipped with, which
# is true of an inspection appliance and equally true of a company's own
# certificate authority. internal-ca.txt is the same value reached honestly, and
# the two files only mean anything as a pair.
authority_held_by=some_stores

# THE EVIDENCE TRAVELS WITH THE CLAIM - inviolable rule 21. Both of these are
# facts off the wire rather than conclusions, and the issuer being recognisable
# by eye is not what produced the finding.
authority_issuer_contains=mitmproxy
authority_has_fingerprint=yes

# NOT YET, AND NOT BY STRUCTURE EVER. The word belongs to K2 and to a match
# against the inspection-product list. A "no" here is a pass rather than a gap.
authority_accuses_interception=no

# --- the command ---
#
# THE STORE IS THE FAULT HERE EVEN THOUGH THE CHAIN IS INCOMPLETE, and that is
# the case ADR51's first gate got wrong. It refused a command whenever the chain
# was incomplete, because a server withholding its intermediate turns every store
# red through no fault of the machine. A middlebox signing straight from its own
# root produces the same incompleteness for the OPPOSITE reason, and adding the
# certificate is precisely the repair.
#
# WHAT SEPARATES THE TWO IS POSITIVE PROOF RATHER THAN A GUESS: another store on
# this very machine closed this very chain. An anchor that closes it therefore
# exists, so the store that refused can be repaired by being given it. On
# no-intermediate.txt no store closes it, and no command is offered there.
#
# The two stores are written into a working directory rather than into this
# account's own files, so an ordinary account could not edit them - which is the
# same answer /etc/ssl/certs gives on private-root.txt, reached the same way.
remediation_expected=yes
remediation_requires_elevation=yes
remediation_has_placeholders=yes
remediation_forbidden=CURL_CA_BUNDLE=,--cacert,sslCAInfo

exit_code=4
